# 03 — ERC-8004 Identity + Reputation (Fuji)

**Mục tiêu:** agent có identity đọc được on-chain và reputation tích
lũy từ những lần làm việc thật đã trả tiền. Không làm validation
registry trong MVP.

## 2. Identity — đăng ký 1 agent demo, dùng xuyên suốt

```solidity
// IdentityRegistry (ERC-721 based)
function register(string calldata agentURI) external returns (uint256 agentId);
```

- `agentURI`: trỏ tới file JSON mô tả agent (tên, mô tả, tools nó
  bán/dùng, `x402Support: true`, payment wallet). File này để ở đâu
  cũng được miễn là đọc được công khai trong lúc chấm (repo public,
  hoặc host tĩnh) — URI chết lúc chấm là mất điểm trust layer.
- Sau `register()`, ghi lại ngay: `agentId`, payment wallet bound,
  tx hash, và URI. Điền vào app config, slides, video.
- Frontend đọc lại: `agentId` + owner + URI, hiển thị ở dashboard
  scene 1 của demo (20 giây, xem 07).
- **Không đăng ký lại agent mới mỗi lần demo.** Một agentId, tích lũy
  reputation qua nhiều lần — đăng ký mới là xóa lịch sử, phản tác
  dụng của reputation.

## 3. Reputation — feedback chỉ sau khi call thành công và đã trả tiền

### 3.1. Hàm và tham số (ERC-8004 chuẩn)

```solidity
function giveFeedback(
    uint256 agentId,
    int128 value,          // điểm có dấu, fixed-point
    uint8 valueDecimals,   // 0–18
    string calldata tag1,
    string calldata tag2,
    string calldata endpoint,
    string calldata feedbackURI,
    bytes32 feedbackHash   // keccak256 của file feedback off-chain
) external;
```

**Quy tắc chuẩn phải tôn trọng:**

- Người feedback **không được là owner/operator của chính agent đó**
  — self-feedback bị reject. Vì vậy demo feedback phải gọi từ ví
  client (người mua tool), không phải ví agent.
- `agentId` phải tồn tại (đã register).
- `valueDecimals` 0–18.

### 3.2. Tag và điểm dùng trong MVP — chỉ 2 loại, đừng sáng tác thêm tag

| tag1 | tag2 | value | valueDecimals | Khi nào dùng |
|---|---|---|---|---|
| `successRate` | `completed-call` | `100` (= 100%) hoặc `0` | `0` | Sau mỗi tool call thành công (100) hoặc fail đã charge? Không — chỉ feedback khi call hoàn thành và đã settle. Fail không charge thì không feedback success. |
| `starred` | `demo-client` | `87` (= 87/100, ví dụ) hoặc điểm client chấm 0–100 | `0` | Client chấm chất lượng sau khi nhận kết quả, 1 lần / call |

- File feedback off-chain (JSON) chứa: agentId, client, tool, tx hash
  payment, kết quả tóm tắt, điểm. `feedbackHash = keccak256(file)`.
  File này lưu ở đâu đọc được (repo hoặc host tĩnh), hash on-chain
  để giám khảo kiểm tra file không bị sửa sau.
- Đừng feedback hàng loạt từ cùng 1 ví trong 1 phút để "làm đẹp"
  reputation — giám khảo đọc được timestamp và client, và đó là
  Sybil pattern, phản tác dụng.

### 3.3. Đọc reputation — summary cần trusted clients

```solidity
function getSummary(uint256 agentId, address[] calldata clientAddresses, string calldata tag1)
    external view returns (uint64 count, int128 summaryValue, uint8 decimals);
```

- `getSummary` yêu cầu caller cung cấp danh sách client tin cậy
  (`clientAddresses` không rỗng) — summary tính trên feedback từ
  những client đó, không phải trung bình tất cả mọi người.
- Frontend MVP: truyền danh sách client demo đã feedback thật
  (ví dụ 1–3 ví client demo), hiển thị `count`, `summaryValue`,
  `decimals` đúng như contract trả, không tự tính trung bình riêng
  rồi ghi là "on-chain score".
- Đọc thêm: `getFeedback(agentId)` để liệt kê từng feedback nếu UI
  cần chi tiết.

## 4. Reputation dùng để làm gì trong MVP — và không dùng để làm gì

**Dùng:**

- Hiển thị trust ở dashboard và scene demo 1: agent này là ai, đã
  hoàn thành bao nhiêu call có trả tiền, điểm trung bình từ client
  tin cậy là bao nhiêu.
- Audit proof bundle (09): mỗi lần feedback gắn với tx hash payment
  tương ứng, tạo chuỗi "trả tiền → làm việc → được chấm" kiểm chứng được.

**Không dùng trong MVP (ghi rõ để khỏi bị hỏi vặn):**

- Không dùng reputation để tự động tăng cap hay mở allowlist — vì
  reputation chưa chống Sybil, tăng quyền theo điểm là tạo đường
  farm điểm để mở quyền. Đây là stretch có kiểm soát ở 09, không
  phải MVP.
- Không gọi reputation là "điểm tin cậy tuyệt đối" hay "chống gian
  lận". Câu đúng: "tín hiệu từ client đã trả tiền, đọc được on-chain,
  ai cũng kiểm tra được nguồn".

## 5. Luồng demo cho trust layer (20 giây, scene 1)

1. Dashboard hiển thị agentId + URI + payment wallet (đọc từ Identity).
2. Hiển thị count + summary từ Reputation (đọc từ `getSummary` với
   trusted clients demo).
3. Sau mỗi tool call thành công ở scene 2, client feedback 1 lần,
   tx hash feedback hiển thị ngay — giám khảo thấy reputation tăng
   lên từ công việc thật, không phải số bịa.

## 6. Test bắt buộc

- Register → đọc lại agentId, owner, URI đúng.
- Feedback từ client (không phải owner) → success, đọc lại được.
- Self-feedback từ owner → revert (test này chứng minh team hiểu chuẩn).
- `getSummary` với trusted clients rỗng → fail theo chuẩn, frontend
  không được crash mà hiển thị "chưa có trusted client".
- Feedback cho agentId không tồn tại → revert.
